# Image Uploads — Architecture & Security

Centralized secure image upload system for the Admin Panel (replaces the
old "paste an image URL" workflow on image fields).

## Where uploaded images live

| Kind | Storage directory | Public URL |
|---|---|---|
| Generic CMS images (news, hero, life grid, video thumbnails, logo, OG image) | `server/src/uploads/images/` | `/api/uploads/images/<file>` |
| Leadership portraits | `server/src/uploads/leadership/` | `/api/uploads/leadership/<file>` |

Both directories contain ONLY sanitized, server-generated files and are
gitignored. Files are served by `server/src/routes/uploadsRoutes.js`
(`/api/uploads/...`) with strict filename validation.

## Upload API

```
POST /api/admin/uploads/image
Content-Type: multipart/form-data   (single part named "image")
Auth: admin session cookie (HttpOnly) — same adminAuth as all /api/admin/*
```

Responses:

| Case | Status | Body |
|---|---|---|
| Valid image | `201` | `{ success, data: { image_path, width, height, bytes } }` |
| Unauthenticated | `401` | safe message |
| Wrong content wrapper | `400` | safe message |
| Fake/unsupported/malformed image | `400` | safe message |
| Over 10 MB | `413` | "Image is too large. Maximum allowed size is 10 MB." |
| Dimensions over 6000×6000 / 24 MP | `400` | safe message |
| Rate limited (dedicated limiter) | `429` | safe message |
| Unexpected server fault | `500` | generic message, no internals |

The `image_path` returned is the value stored in database fields
(`news_items.image`, `page_sections` content, `site_settings` branding).

## Allowed formats & limits

- **Formats in:** JPEG, PNG, WebP (validated by magic bytes AND by full decode)
- **Format out:** WebP (server re-encodes everything)
- **Max size:** 10 MB per upload (enforced while streaming, before processing)
- **Max dimensions:** 6000×6000 px per side, 24 MP total (decompression-bomb bound)
- **Processing timeout:** 20 s per image
- **Rate limit:** 30 uploads / 15 min / IP (dedicated to the upload endpoint;
  independent of the global API limiter and the login limiter)

Explicitly rejected: SVG, GIF, ICO, HTML, executables, PDFs, ZIPs, and every
other format — including any file whose declared extension lies about its
content.

## Processing pipeline

```
multipart upload
  → adminAuth (before any bytes are read)
  → dedicated upload rate limiter
  → streaming read with hard 10 MB cap (rejects early)
  → magic-byte allowlist check (cheap pre-gate)
  → sharp: decode with limitInputPixels (24 MP hard backstop)
  → dimension check on the decoded metadata (before full processing)
  → EXIF auto-rotate + metadata stripped (EXIF/GPS not copied to output)
  → re-encode to WebP (quality 82) — freshly generated bytes
  → write to the managed directory under a server-generated filename
  → original upload bytes are discarded, never written to disk
```

Filename scheme: `<base36 timestamp>-<24 hex random chars>.webp`.
Browser-supplied filenames never reach the filesystem, so path traversal is
impossible by construction; storage paths are server-controlled constants.

## How Admin uses it

Every migrated image field shows an **ImageUploader** control:
Choose Image → preview → automatic upload → the stored path is kept in the
form. Replace and Remove buttons manage the value. The control states:
"Accepted: JPG, PNG, WebP · Maximum: 10 MB".

Fields using the uploader:

| Admin page | Field | Old workflow |
|---|---|---|
| Content Center → News & Notices | Item image | manual URL/path text input |
| Homepage | Hero slide images | manual URL/path text input |
| Homepage | Life at School grid images | manual URL/path text input |
| Homepage | Video Showcase thumbnails | manual URL/path text input |
| Site Settings | Logo | manual URL/path text input |
| Site Settings | OG Image | manual URL/path text input |
| Leadership Management | Portrait | dedicated uploader (now on the same sanitizer) |

**Deliberate exception:** Site Settings → Favicon remains a manual path/URL
field. Browsers require SVG/ICO favicon files, which the JPEG/PNG/WebP
pipeline cannot produce, and SVG is rejected by the uploader by policy. A
favicon pipeline would need a separate security review. Favicon uploads via
the general uploader are intentionally impossible.

## Handling of old image references

Existing records keep their stored values and keep rendering:

- legacy site assets (`/Activity/...`, `/Hero Section/...`, `/logo.jpg`)
  live in `client/public` and are served by the public site as before;
- leadership paths under `/api/uploads/leadership/` continue to be served;
- uploaded images from this system live under `/api/uploads/images/`.

The Admin forms still display any of these existing values; only NEW images
must go through the uploader. No mass migration was performed.

## Orphan strategy (non-destructive)

Replacing or removing an image only changes the reference stored in the
database row. Physical deletion of an unreferenced upload happens only where
the reference can be verified:

- **News:** on update/delete, the service checks whether any other news row
  still references the old `/api/uploads/images/...` path before unlinking it.
- **Leadership:** same reference-checked cleanup as before (unchanged).
- **Homepage/Settings:** image values live inside JSON blobs; no cross-record
  reference check exists there, so old files are deliberately KEPT on disk
  when replaced. Cleanup for these is a manual, audited operation
  (`server/src/uploads/images/`) — never automatic.

Legacy paths outside `/api/uploads/` are never deleted by application code.

## Security considerations & honest limitations

Implemented controls: admin-only access (no public upload), dedicated rate
limit, streaming size cap, magic-byte allowlist, full decode validation,
dimension/pixel limits, metadata stripping, re-encoding to a single output
format, server-generated filenames, containment-checked serving paths, and
safe generic error messages (no stack traces, paths, or library details).

Limitations, stated plainly:

- Re-encoding is defense in depth, **not** a malware guarantee. It defeats
  most content-spoofing and polyglot tricks but is not a sandboxed antivirus.
- "All metadata removed" is not claimed: the most sensitive classes (EXIF,
  GPS) are not copied by the pipeline; exotic metadata carriers are not
  exhaustively enumerated.
- Authorization is binary (any authenticated admin) — there are no granular
  upload roles to check against.
- The JSON-blob fields (homepage/settings) cannot prove a file is unreferenced
  before deletion, so the system keeps files instead of risking broken images.
